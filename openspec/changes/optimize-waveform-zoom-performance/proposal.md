# Proposal

## Why

На длинных миксах зум работает медленно: детальная волна каждый раз декодируется с начала файла до конца запрошенного окна, а UI запрашивает её на каждое изменение зума или панорамы. Дополнительно при быстром Zoom Out появляется пустая область: canvas очищается, detail-окно покрывает только часть нового вьюпорта, а overview как fallback не рисуется.

Текущая архитектура не использует стандартный для волн подход — предрасчитанную многоуровневую пиковую пирамиду, из которой вьюпорт собирается за число операций порядка ширины canvas.

## What Changes

- **Пиковая пирамида при анализе.** В существующем проходе `decode_overview` строится finest-уровень min/max-пиков с шагом около 128 кадров (~3 мс при 44.1/48 кГц). Более грубые уровни строятся из него в UI за один проход, без повторного декодирования.
- **Кэш waveform версии 3.** Хранит overview `500` бинов и finest-уровень пиков. Старые кэши пересоздаются один раз; `config.json`, SQLite и пользовательские данные не меняются.
- **Клиентский рендер зума.** Пики один раз передаются в WebView компактным base64-payload. JS строит mip-уровни и на каждый кадр агрегирует 1–2 бина на пиксель. Зум и панорама не декодируют аудио, не запрашивают бэкенд и не перерисовывают Dioxus-дерево на каждый тик колеса.
- **Progressive fallback без пустых участков.** Базовый слой рисуется на всю ширину из mip, иначе overview, иначе placeholder. Detail накладывается только на свой диапазон. Быстрый Zoom Out сразу показывает более грубую форму сигнала по всей ширине; canvas не остаётся прозрачным там, где есть данные.
- **Крайний зум за пределами разрешения пиков.** Декодируется только локальное окно около трёх экранов (максимум несколько секунд), результат кэшируется в LRU и переиспользуется при зуме туда-обратно. Для выравнивания используется точный seek; существующий конструктор декодера параметризуется режимом seek, отдельная сущность не вводится.
- **Ограничение частоты синхронизации вьюпорта.** Canvas обновляется в `requestAnimationFrame` сразу, а сигналы `zoom`/`view_center` для loop-оверлеев и шкалы — с ограничением частоты.
- **Оптимизация canvas.** Агрегация по пикселям, `fillRect` и батчинг цветов при плотной волне, отказ от `roundRect`/`beginPath` на каждый бин и от LERP-прохода по всем бинам.
- **Тесты и метрики.** Unit/integration-тесты Rust, Node-тесты извлечённого JS на LOD, агрегацию и отсутствие пустых колонок, debug-объект `window.waveformStats` для ручных замеров.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `player/waveform-loop`: зум и панорама должны рендериться из предрасчитанной пиковой пирамиды, не оставлять пустых участков и не декодировать аудио в основном пути.

## Impact

**Backend:** `src/backend/analysis/service.rs` — построение пиков, событие с payload, replay, локальные окна; `src/backend/waveform_cache.rs` — формат кэша v3; `src/backend/decoder.rs` — режим seek; `src/shared/event_types.rs` — событие `WaveformPeaksReady`.

**UI:** `src/gui/components/waveform_bins_canvas.rs` — mip-рендер, композиция слоёв, LRU локальных окон, ограничение синхронизации; `src/gui/components/waveform.rs` — ширина canvas и совместимость с оверлеями.

**Данные и конфигурация:** меняется только формат waveform-кэша (версия 3). SQLite-схема и миграции не меняются.

**Зависимости:** новые не добавляются; `base64` уже есть в `Cargo.toml`.

**Тесты:** Rust unit/integration, Node-тесты `tests/waveform_pyramid.test.cjs`, manual smoke в WebView. E2E не добавляются.

## Non-goals

- Изменение поведения воспроизведения, seek, loop-региона, beat grid и шкалы времени.
- Изменение максимального зума: крайний зум остаётся доступным, но обслуживается локальными окнами.
- Визуальный редизайн волны: сохраняются столбики от центра, цвета played/unplayed и общая анимация появления.
- Раздельная отрисовка левого и правого каналов: волна остаётся моно-суммой min/max по каналам.
- Изменение результатов анализа BPM, ключа и LUFS.
- Полноценный tiled cache, отдельный scheduler с очередями приоритетов и raster/bitmap-кэш: finest-уровень строится целиком и помещается в память; при необходимости они могут стать отдельным change.
- Автоматические e2e/UI-тесты и новые CI-задачи.

## Assumptions

- Разовая передача около 2.5 МБ бинарных пиков (3.3 МБ base64) для часового трека и построение mip-уровней в JS занимают десятки миллисекунд и не заметны на фоне загрузки трека.
- WebView эффективно хранит `Int8Array` на несколько мегабайт и рисует около 1200–2000 `fillRect` за кадр.
- Целевые форматы поддерживают точный seek; для остальных сохраняется корректный резервный последовательный путь.
- Ограничение finest-уровня четырьмя миллионами бинов (до ~8 МБ кэша на файл) приемлемо; для экстремально длинных файлов шаг пиков увеличивается, а глубокий зум переходит на локальные окна.
