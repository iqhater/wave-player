# Design

## Context

См. `proposal.md` — Why.

Текущий путь анализа (`src/backend/analysis/service.rs`):

1. `analyze_track` проверяет кэш и при отсутствии `bpm_key` вызывает `decode_mono(job)`.
2. `decode_mono` открывает декодер, читает **весь файл** покадрово и складывает моно-сумму в `Vec<f32>` без верхней границы (`Vec::new()` + `push`).
3. `analyze_bpm_key` передаёт этот срез целиком в `stratum_dsp::analyze_audio`.

Для часового файла при 44.1 кГц это 158 760 000 `f32` ≈ 635 МБ только во входном векторе. Дополнительно `Vec` растёт удвоением, поэтому пиковая память включает копию при реаллокации, а `stratum-dsp` строит собственные буферы и спектрограммы пропорционально длине входа. Отсюда высокое потребление RAM и вылеты.

Кэш анализа хранит `bpm_key` и `bpm_key_version`. `parse_cache` уже умеет сбрасывать только `bpm_key` при несовпадении версии, сохраняя waveform и LUFS.

Beat grid в UI (`src/gui/components/beat_grid.rs`) использует только первый элемент `beats`/`bars` как фазу и достраивает равномерную сетку на всю длительность; `snapToGrid` устроен так же. Поэтому частичный список битов не ломает отрисовку за пределами окна.

## Goals / Non-Goals

**Goals:**

- Ограничить объём входного буфера и длительность работы BPM/key анализа.
- Сохранить текущий контракт `PlayerEvent::BpmKeyDetected`, запись в `tracks.bpm`/`tracks.key` и формат кэша анализа.
- Не менять результат для треков короче окна.
- Пересчитать один раз старые результаты, посчитанные по всему файлу.

**Non-Goals:**

- Настройка окна через UI или `config.json`.
- Многократный анализ, анализ по loop-региону или по всему миксу.
- Изменение waveform/LUFS анализа и JS-отрисовки beat grid.
- Замена или патчинг `stratum-dsp`.

## Decisions

### D1. Ограничение в `decode_mono`, а не в `analyze_bpm_key` или UI

`decode_mono` — единственное место, где создаётся неограниченный буфер; он же выполняет дорогое декодирование. Ограничение здесь уменьшает и память, и время. `analyze_bpm_key` остаётся функцией «проанализируй переданные сэмплы», поэтому её можно позже переиспользовать для окон другого размера.

Альтернативы:

- Обрезать срез в `analyze_bpm_key` — не помогает: полный файл уже декодирован и лежит в памяти.
- Ограничивать в UI — не защищает от `Reanalyze`, прямых вызовов движка и не ограничивает backend.

### D2. Окно задаётся временем и абсолютным лимитом кадров

Константы в `service.rs`:

```rust
const BPM_KEY_WINDOW: Duration = Duration::from_secs(10 * 60);
// 10 минут при 48 кГц; защита от высоких частот дискретизации.
const BPM_KEY_MAX_FRAMES: u64 = 28_800_000;
```

Чистая функция вычисляет границу кадров:

```rust
fn bpm_key_frame_limit(duration: Duration, sample_rate: u32) -> usize
```

Правило: `min(кадры_длительности, sample_rate × 600, BPM_KEY_MAX_FRAMES)` с насыщающей арифметикой. Для трека короче окна лимит равен полной длительности, поэтому поведение не меняется. Верхний предел по кадрам не даёт файлам 96/192 кГц занять сотни мегабайт; для них анализируется меньший отрезок времени (5/2.5 минуты), что приемлемо для оценки BPM и ключа.

Альтернативы:

- Только временное окно — при 192 кГц 10 минут дают ~460 МБ, что не решает проблему вылетов.
- Только лимит кадров — для 44.1 кГц он дал бы ~10.9 минуты, что сложнее объяснить и проверить; комбинация точнее соответствует требованию «10 минут».

### D3. Предвыделение буфера

`Vec::with_capacity(frame_limit)` вместо роста через `push`. Верхняя граница уже известна, поэтому пиковая память не включает промежуточные копии при удвоении. Для коротких треков capacity соответствует их длительности, а не окну.

### D4. Версия результата `BPM_KEY_VERSION` = 3

Старые записи `bpm_key` посчитаны по всему файлу и не должны переиспользоваться: иначе пользователь не увидит эффекта до ручного `Reanalyze`. `parse_cache` сбрасывает только `bpm_key` и обновляет версию; `loudness` и waveform остаются. SQLite и `config.json` не меняются.

Альтернатива — не менять версию и ждать ручного `Reanalyze`: непредсказуемо для пользователя и оставляет старые тяжёлые beat grid в кэше.

### D5. UI и beat grid не меняются

`beat_grid.rs` уже строит равномерную сетку от фазы первого бита на всю длительность, а `offset` берётся из первого downbeat. Для треков длиннее окна массивы `beats`/`bars` короче длительности, но UI читает только первый элемент. Это сохраняемое поведение: менять JS или добавлять индикацию «проанализировано 10 минут» в этом change не нужно.

### D6. Одинаковое поведение для обычного анализа и `Reanalyze`

`restart` использует тот же `TrackJob` и тот же `decode_mono`, поэтому окно применяется и к ручному пересчёту. Отдельная ветка не нужна.

## Data Flow

```
TrackJob { path, duration }
  └─ analyze_track
       ├─ decode_overview (полный трек, потоково, память фиксирована) — без изменений
       ├─ decode_mono (только frame_limit кадров)
       │    └─ analyze_bpm_key(&samples, sample_rate, 1) — без изменений
       ├─ persist → CachedAnalysis { bpm_key, bpm_key_version: 3 }
       │    └─ StoreCommand::UpdateTrackAnalysis — без изменений
       └─ PlayerEvent::BpmKeyDetected — без изменений
```

## Error Handling

- Пустое окно (повреждённый файл, нулевая длительность) → существующая ошибка `audio contains no samples`; плеер продолжает работу.
- Ошибка `stratum-dsp` → `AudioError::FileCorrupted`, логируется в `analyze_track`, воспроизведение не затрагивается.
- Отмена и смена трека → проверки `Token::check()` каждые 4096 кадров сохраняются; цикл прерывается на границе окна так же, как раньше на EOF.
- Некорректная длительность из метаданных не может увеличить буфер: цикл жёстко ограничен `frame_limit`.

## Risks / Trade-offs

- **Точность BPM/ключа на миксах.** Результат теперь описывает начало трека, а не весь микс. Для миксов это соответствует замыслу; для треков с переменным темпом возможна меньшая точность. → Окно 10 минут, manual smoke на нескольких длинных файлах.
- **Память внутри `stratum-dsp`.** Входной буфер ограничен, но внутренние аллокации библиотеки могут быть кратны ему. → Лимит кадров и проверка памяти на часовом миксе; при необходимости уменьшение окна станет отдельным change.
- **Высокие частоты дискретизации.** При 96/192 кГц анализируется 5/2.5 минуты. → Это осознанный компромисс ради верхней границы памяти; для обычных 44.1/48 кГц доступны полные 10 минут.
- **Beat grid за пределами окна.** Сетка равномерная и может расходиться с реальным темпом, если он меняется в миксе. → Такое поведение уже есть: UI всегда достраивает сетку от первого бита.
- **Старый кэш.** Без повышения версии результат полного анализа остался бы навсегда. → `BPM_KEY_VERSION` = 3 и существующий механизм `parse_cache`.

## Migration Plan

Миграция данных не требуется.

1. При первом запуске новой версии `parse_cache` видит `bpm_key_version`, отличную от 3, и сбрасывает только `bpm_key`.
2. Повторный анализ выполняется по окну; waveform и LUFS берутся из существующего кэша.
3. Откат безопасен: старая версия увидит неизвестную версию, сбросит `bpm_key` и пересчитает его по всему файлу, не затрагивая waveform и LUFS.

## Test Plan

| Требование | Проверка |
| --- | --- |
| Ограничение первыми 10 минутами | unit-тесты `bpm_key_frame_limit`: 60 мин при 44.1 кГц → 26 460 000; 192 кГц → `BPM_KEY_MAX_FRAMES`; насыщение при больших значениях |
| Короткие треки полностью | unit-тесты: 3 мин → все кадры; ровно 10 мин → все кадры без потери последнего |
| Пересчёт старого кэша | unit-тест `parse_cache` с `bpm_key_version = 2`: `bpm_key` отсутствует, `loudness` и waveform сохранены |
| Beat grid за окном | существующие `tests/beat_grid.test.cjs` (фаза и snapping) + manual smoke |
| Фоновый анализ | manual smoke: воспроизведение и loop во время анализа часового файла |

Дополнительно: unit-тест `decode_mono` на маленьком WAV-фикстуре подтверждает, что при длительности меньше окна декодируются все кадры и моно-суммирование не изменилось. Полный 10-минутный фикстур не создаётся — это дорого по памяти и времени; граница окна покрывается чистой функцией, а end-to-end поведение — manual smoke. Существующие тесты `write_test_wav` переиспользуются.

Ожидаемое покрытие новой чистой логики — 100%; `decode_mono` покрывается коротким фикстуром. Mutation testing не требуется: change не добавляет новую предметную логику, а меняет границу ресурса; при желании допустим 5-минутный прогон только по `service.rs`.
